# Root-cause analysis of the six weak questions

Sources are the individual reviews in `docs/dedicated-quiz-evaluation.md`, the fictional API results under `work/dedicated-eval`, and the previous browser transcript. All six had correct keys in the earlier review. These findings concern the alternatives and feedback, not a newly established incorrect key.

1. **Mixed checkout, API question 2.** Given the explicitly nonempty `[5]` list, option D claims both calls take the empty-cart error branch. That is easy to eliminate because the very first guard tests list truthiness and is independent of coupon capitalization. It does not reflect a meaningful misunderstanding of the code under the stated premises. The useful alternatives instead confuse case-sensitive comparison and floor versus ordinary division. The option-specific feedback accurately cites the guard but only diagnoses an implausible wrong path.
2. **Java validation, question 1.** With price 25 and quantity 0, distractor A says both versions return zero. Distractor C says the old version returns zero and the new version calls `Math.multiplyExact(25, 0)`. Under normal Java semantics C implies the same final zero result as A. The asked observable is what happens to the call, but one option is an outcome and the other is an execution path with the same implied outcome. The model distinguished phrasing rather than comparing consequences. Its feedback explains the guard separately but never compares the two alternatives.
3. **Java validation, question 2.** For positive quantity 2, option D claims the new guard throws specifically because quantity is positive, directly reversing a visible `quantity <= 0` condition. Option B also invents an absolute-value conversion. Neither is well motivated by the shown change. Option A is a more realistic confusion between price and quantity validation. Here the exercise degenerates into recognizing an obvious operator, despite a correct answer and explicit premises.
4. **SQL inventory, question 1.** At stock zero, option D has the old statement decrement to -1 while the new statement increases stock to 1. The only shown assignment is `stock = stock - 1`; the diff adds a filter, not an increment. This supplies an arbitrary outcome rather than a plausible error about whether a predicate filters the row. Other choices reflect missing or incorrectly applying the guard.
5. **SQL inventory, question 2.** At stock 2, option B says one statement changes stock to 0 and returns 0. No shown operation repeats the decrement; the stated premise says one matching row and one execution. The wrong answer is invented arithmetic, rather than a plausible misreading of the return-before/return-after semantics. Options A and D respectively reflect a believable old-value/updated-value confusion and an incorrect filter decision.
6. **Browser mixed checkout, question 1.** For an explicitly empty list with the coupon, choice A says both versions return zero/200. Choice C says the old and new versions return zero/200 because the coupon is valid. The causal explanation differs but the old/new observable return tuple is identical, which violates the requirement that each answer describe a distinct outcome. The user was asked specifically about returned values, so an extra rationale cannot make the alternatives distinct. Both distractor explanations describe failures to account for the guard.

## Recurring patterns and limits of the current contract

- **Outcome versus mechanism mixing.** The Java and browser questions used distinct wording or explanations for identical observable outcomes. The prompt already tells the model to reject overlapping outcomes, but neither the output schema nor structural validator represents the outcome separately. Free-text alternatives and feedback do not expose a dependable canonical state. Exact string checks cannot reliably detect this form of equivalence.
- **Distractor filling without a defensible misconception.** The checkout, Java and SQL weak options select an impossible or arbitrary branch/result even under explicit inputs. The instruction asks for plausible, distinct misunderstandings, but providing four strings and four explanations does not ensure any misconception is realistic. An explanation that disproves an alternative does not prove that a skilled developer might plausibly choose it.
- **Question premises and feedback are mostly adequate here.** All six have explicit inputs and the original review judged each key correct. The issue is alternative quality, with some simple branches providing too little conceptual material to make three competitive distractors. The option-specific feedback contract can explain a selected misconception and cite question-level lines, but its prose is itself unverified and does not supply per-option citations. The current examples do not demonstrate a need to expand the schema.
- **No mechanical semantic guarantee.** Existing validation enforces format, four nonempty unique normalized option strings, a bounded answer index, duplicate-question checks, reference validity and option-feedback shape. It cannot evaluate program behavior, determine semantic equivalence, or grade plausibility. A blanket token-overlap rule would reject legitimate alternatives differing in boundary values, error status or returned state. Any new deterministic check needs a lossless contract and a narrow, verified trigger.

Suggested prompt direction is to privately select a behavior, derive its evidence-backed correct outcome, then derive wrong outcomes from distinct concrete misconceptions and compare each complete observable result with all other choices. Do not display those private notes. When the code cannot support three believable distinct incorrect outcomes, omit the question. This may reduce counts, which should be measured rather than assumed to improve quality.
